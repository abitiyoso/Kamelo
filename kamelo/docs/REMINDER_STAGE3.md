# Stage 3 — Scheduled billing reminders

20 October 2026. Local implementation extends the existing application. Public pages, approved artwork, green backoffice identity, menu order, financial ledgers and authentication are retained. This is local readiness, not production channel acceptance.

## Behavior

The owner chooses one property in Tagihan & Pembayaran and explicitly confirms its reminder policy. Defaults are disabled: portal off, email off, 09:00 Jakarta, zero days before due and a three-day rolling interval. Hour is 0–23, lead window 0–30 days and interval 1–30 days. Policy updates require the current revision and an idempotency key. Staff, tenants and other organizations cannot configure, preview or run the policy.

The scheduler publishes private portal snapshots and optionally queues encrypted transactional emails. Issued invoices and active opening balances must have positive current unpaid amounts, reach the configured due window and have no pending proof. Future-issued invoices and future-as-of opening batches are excluded. The recipient must be a verified, active account with a fresh billing grant for the exact stay. Opening balances additionally require the existing explicit account/stay/grant share. Guest phone numbers or contact matches never grant access. The owner who configured the policy must still have active owner membership.

The job takes the same organization advisory lock as canonical financial/access writes. Each channel has a source-level rolling cooldown, plus a same-recipient/source/day dedupe key. Recent source attempts conservatively consume the interval even if later cancelled or blocked. Recent manual opening portal reminders suppress automatic publication for 24 hours; an automatic portal publication also suppresses the existing manual reminder for 24 hours. Pending/processing/UNKNOWN email blocks another automatic email for that source beyond the interval. Unknown delivery needs operator investigation; there is no automatic resend control.

Each property processes at most twenty eligible sources per channel per call. SQL excludes suppressed sources before limiting, so repeat calls progress to later sources. Job pagination covers ten enabled properties at a time and returns a cursor. The worker follows cursors and repeats every minute. Scheduled hour means eligible at/after that hour, not guaranteed execution at precisely that minute. No worker service is silently installed.

Portal publication is PUBLISHED, not read/delivered confirmation. Tenant home keeps its original balance/services first, shows the latest three reminders, and expands to private twenty-row history with independent pagination and refresh. Amounts are immutable historical snapshots; tenant copy directs the user to live tagihan for the current balance and pending proof state. Revoked billing access hides the history immediately on a fresh request. Revoked opening shares hide their associated history; a replacement tenant does not inherit it.

## Email and safety boundaries

The optional channel uses the existing encrypted outbox and Hostinger transport, with a new generic payment-reminder template. Its body contains a portal link and no reference, amount, due date, property name or other financial snapshot. Existing live-send gate, recipient allowlist, TLS and sink-only restrictions remain intact. The migration/feature does not activate SMTP.

Before dispatch, the mail worker takes the organization lock and rechecks policy/revision/owner, recipient verification/address hash, billing grant, opening share, pending proof and canonical source amount/due/reference. Changed, paid, void, expired or revoked items become CANCELLED with an erased encrypted payload. An accepted message or one already handed to transport cannot be recalled; the generic body avoids promising a stale balance. There remains a short unavoidable interval between the last database check and external transport handoff.

Email delivery rows retain QUEUED as their immutable creation state unless cancelled. The owner's display derives current transport state from the linked EmailOutbox: QUEUED, PROCESSING, SINKED, ACCEPTED, BLOCKED, FAILED, UNKNOWN or CANCELLED. SINKED means a local test file; ACCEPTED means accepted by the email provider, not inbox/read acceptance. No WhatsApp is automatically sent. Notifications never create a Payment, OpeningReceipt, invoice, deposit entry or change a balance.

## Run and validate

After an approved migration, use the existing server-only OPERATIONS_JOB_KEY (at least 64 random characters) and correct APP_URL for server and workers. Start `pnpm worker:reminders`; use `pnpm worker:mail` separately to drain emails. Enabling a property policy does not start these processes. Workers need process supervision in the eventual production environment. MAIL_DRIVER defaults to disabled; QA uses sink and MAIL_LIVE_ENABLED=false. Do not place job/encryption/SMTP keys in public variables or review exports.

QA: build and TypeScript pass, 49 unit tests pass, all 23 integration suites pass including 17 reminder groups. Scenarios include access/CSRF, exact retry/revision bounds, fresh first-publication races, interval/day dedupe, no implicit sharing, current amount changes, settlement, proof upload, policy disable, revoked owner/grant/share, email address changes, expiration, UNKNOWN persistence, provider/sink state, batch progress and private history pagination. Ledger preservation and no-store/private metadata checks pass. Owner save/run/history and resident history/bill navigation are browser checked; 320/390 px screenshots and metrics accompany the report.

Stage 3 of the six-stage delivery plan is complete locally. Stages 4–6 remain: finance completion, configured real integration acceptance, and final release acceptance.
